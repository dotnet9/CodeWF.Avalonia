# Markdown 基准报告

> 测量工具：`bench/CodeWF.Avalonia.Markdown.Benchmarks`（控制台 harness，`dotnet run -c Release -- all`）。
> 每个优化落点在此登记"改动前 / 改动后"数据对照；没有数据的优化不合并。

## 环境

- .NET 10.0.303 / Windows 11 x64 / Release
- 文档样本：确定性生成（标题/段落/列表/表格/代码块/引用/任务列表循环，见 `DocumentBuilder`）
- 分配统计：`GC.GetTotalAllocatedBytes(precise: true)`

## 基线（2026-10-19，流式内核实施前）

| 场景 | 数据 |
|---|---|
| 整篇解析 5 KB | 平均 0.78 ms，最小 0.70 ms，分配 241.9 KB/次 |
| 整篇解析 20 KB | 平均 3.11 ms，最小 2.62 ms，分配 958.8 KB/次 |
| 整篇解析 100 KB | 平均 16.86 ms，最小 12.51 ms，分配 4955.3 KB/次 |
| 逐 token 追加 20 KB / 4 字符 | 5120 步，总 1278 ms，步均 0.25 ms，**总分配 2507.8 MB** |
| 逐 token 追加 20 KB / 32 字符 | 640 步，总 168 ms，步均 0.26 ms，总分配 313.8 MB |

### 基线读数

- 逐 token 追加场景中，块级 diff 只占步均耗时的 **1%**，其余 99% 是整篇 Markdig 解析
  ——现状管线对追加型输入的成本严格 O(全文)，diff 优化救不了解析。
- 20KB 文档按 4 字符/token 流完一遍，产生约 **2.5 GB** 分配（每步 substring 前缀 +
  全篇解析），GC 压力全部落在流式期间。

## 阶段 1 落地后（2026-10-19，流式内核 `MarkdownStreamingDocument`）

| 场景 | 前（现状管线） | 后（流式内核） | 提升 |
|---|---|---|---|
| 20 KB / 4 字符逐 token 追加 | 1278 ms，2507.8 MB | 墙钟 30 ms，105.6 MB | **42× 提速，24× 降分配** |
| 20 KB / 32 字符逐块追加 | 168 ms，313.8 MB | （同机制，冻结粒度不变，略） | — |

读数说明：

- 流式引擎把 5120 次追加在后台合并为少量解析——冻结边界之外只有尾部参与
  重解析，冻结前缀的块模型跨快照对象级共享；墙钟含 ~1ms 轮询粒度。
- 分配残余（105 MB）主要来自每次 Append 的字符串拼接与尾部临时文本解析，
  量级已与文档大小而非步数相关。
- 渲染端复用：快照模型交给现有块级 diff，冻结块哈希不变 → 视觉树只替换尾部
  （headless 测试断言首帧 Full、后续 Incremental）。

## 优化记录

2026-10-21，Mermaid 图鉴对照：Windows / .NET 10.0.303 / Release / Avalonia.Headless + Skia，1280 × 820，22 张真实图表，同一 Vex 工作台代码，仅替换 12.1.4.35 与 12.1.4.36 本地包，顺序运行避免 CPU 争用。首次从源码切到即时编辑首帧 **307.54 → 200.78ms**，第一张图完成 **706.91 → 626.44ms**；阅读显示就绪 **115.11 → 96.31ms**。三次热切换中位数 **188.98 → 162.58ms**，单次存在调度波动，不作为稳定帧率保证。完整 22 图 × 明暗 × 阅读/即时编辑的 88 项组合另行通过。

同轮 `bench ... -- all`：5 / 20 / 100KB 全文解析均值 0.77 / 3.29 / 16.26ms，分配 241.9 / 958.8 / 4952.7KB；20KB / 4 字符流式墙钟 14ms、110.4MB。该基准覆盖解析内核，没有测量图表布局；图表收益以工作台对照为准。
